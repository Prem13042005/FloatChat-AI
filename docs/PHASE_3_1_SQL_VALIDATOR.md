# Phase 3.1 — Deterministic SQL Validator Core Specification

## 1. Purpose

The `DeterministicSQLValidator` (`src/security/sql_validator.py`) provides a deterministic, non-LLM security barrier between the natural language Text-to-SQL generation agent (Phase 3.2+) and the PostgreSQL/PostGIS database instance. 

Its primary purpose is to ensure that generated SQL queries conform strictly to a read-only, schema-bounded, resource-capped execution contract before any query reaches the PostgreSQL database engine.

> [!IMPORTANT]
> The validator operates **strictly without LLM assistance**. It uses AST (Abstract Syntax Tree) parsing via `sqlglot` to inspect and transform incoming queries deterministically.

---

## 2. Security Boundary

The SQL validator forms the **first layer of defense** in the FloatChat security architecture:

```
[User Query]
     │
     ▼
[Text-to-SQL Agent (LLM)]
     │
     ▼ (Generated SQL String)
┌─────────────────────────────────────────────────────────┐
│        DETERMINISTIC SQL VALIDATOR CORE (Phase 3.1)     │
│  - AST Parsing (sqlglot)                                │
│  - Single Statement Enforcement                         │
│  - SELECT-Only Policy                                   │
│  - Schema & Column Whitelisting                         │
│  - Function Whitelisting (PostGIS & Aggregations)      │
│  - Limit Policy (Inject/Cap)                            │
└─────────────────────────────────────────────────────────┘
     │
     ├─────────────► [REJECTED] ──► Return Validation Errors to LLM / User
     ▼ (Validated & Normalized SQL)
[Database Execution Engine (Timeout Wrapper)]
     │
     ▼
[PostgreSQL / PostGIS Database]
```

### Key Security Guarantee
No SQL string generated by an external LLM or received from an external caller can reach the database unless it passes every static AST validation rule defined in `DeterministicSQLValidator`.

---

## 3. AST-Based Validation Approach

Rather than relying on brittle regular expressions or basic keyword searches, `DeterministicSQLValidator` parses incoming SQL strings into AST node structures using `sqlglot` (`read="postgres"` dialect).

### Validation Pipeline Steps
1. **Parse & Structure Check**:
   - `sqlglot.parse(sql, read="postgres")`
   - Rejects empty, whitespace-only, or syntactically invalid SQL.
   - Enforces **exactly one** statement (`len(statements) == 1`).
2. **Statement Type Enforcement**:
   - The single statement root node **must** be an instance of `sqlglot.exp.Select`.
   - Any query containing `SELECT ... INTO`, DDL (`CREATE`, `DROP`, `ALTER`, `TRUNCATE`), DML (`INSERT`, `UPDATE`, `DELETE`), DCL (`GRANT`, `REVOKE`), procedural calls (`CALL`, `EXECUTE`), or copy commands (`COPY`) is immediately rejected.
3. **Table & Schema Whitelisting**:
   - Recursively traverses all `sqlglot.exp.Table` nodes in the AST (including CTEs, subqueries, and JOINs).
   - Validates schema qualifications (`public` or unspecified only; catalog schemas like `pg_catalog` and `information_schema` are rejected).
   - Verifies table names against `ALLOWED_TABLES`.
4. **Column Qualification & Whitelisting**:
   - Inspects all `sqlglot.exp.Column` nodes.
   - Rejects access to unauthorized or non-existent physical columns.
   - Rejects system catalog columns (e.g., `pg_class`, `version()`).
   - Supports wildcards (`SELECT *`), ensuring expansion resolves safely over allowed physical tables.
5. **Function Whitelisting**:
   - Inspects all `sqlglot.exp.Func` and `sqlglot.exp.Anonymous` nodes.
   - Checks function names against `ALLOWED_FUNCTIONS` (standard aggregate, scalar, and PostGIS spatial functions).
   - System routines (e.g., `version()`, `pg_sleep()`, `current_user`) are strictly rejected.
6. **Limit Injection & Enforcement**:
   - Inspects the query's `sqlglot.exp.Limit` node.
   - If missing: automatically injects `LIMIT DEFAULT_LIMIT` (500).
   - If present: caps the limit value to `min(existing_limit, MAX_LIMIT)` (1000).

## 4. Allowed Schema Policy

The validator enforces physical schema bounds strictly based on the Phase 2 PostgreSQL database schema.

### Whitelisted Tables & Columns

| Table Name | Allowed Columns | Description |
| :--- | :--- | :--- |
| `argo_floats` | `platform_number`, `created_at` | ARGO Float Platform Metadata |
| `argo_profiles` | `profile_id`, `platform_number`, `profile_time`, `latitude`, `longitude`, `location` | Individual Profile Casts & PostGIS Geography |
| `argo_measurements` | `measurement_id`, `profile_id`, `pressure_dbar`, `temperature_c`, `salinity_psu` | Physical Hydrographic Observations |

> [!CAUTION]
> Non-existent columns (such as `depth`, `qc_flag`, `quality_flag`, `cycle_number`, `secret_column`) and unauthorized tables (`argo_doc_embeddings`, `users`, `pg_tables`) are **explicitly rejected**.

---

## 5. SELECT-Only Policy

Only standard data retrieval statements (`SELECT`) are permitted.

- **Allowed**: `SELECT`, CTEs (`WITH ... SELECT`), subqueries in `WHERE`/`FROM`/`JOIN`, `GROUP BY`, `ORDER BY`, `HAVING`.
- **Prohibited**:
  - Write operations: `INSERT`, `UPDATE`, `DELETE`
  - Structural modifications: `DROP`, `ALTER`, `TRUNCATE`, `CREATE`
  - Privilege changes: `GRANT`, `REVOKE`
  - Bulk transfers / execution: `COPY`, `CALL`, `EXECUTE`, `PREPARE`
  - Table creation via SELECT: `SELECT ... INTO`

---

## 6. LIMIT Policy

To prevent Memory/CPU Denial of Service (DoS) from unconstrained full table scans, the validator enforces a strict, deterministic result limit policy:

- **Default Limit**: `500` rows.
- **Maximum Ceiling**: `1000` rows.
- **Behavior**:
  - **No `LIMIT` clause provided**: The validator automatically injects `LIMIT 500` into the AST.
  - **`LIMIT N` where `N <= 1000`**: Preserved as `N`.
  - **`LIMIT N` where `N > 1000`**: Safely capped down to `1000`.

---

## 7. PostGIS & Aggregate Function Policy

To support complex spatial and analytical queries without permitting dangerous or arbitrary procedural calls, the validator uses an explicit **Function Whitelist**.

### Whitelisted Functions

```python
ALLOWED_FUNCTIONS = {
    # Aggregate Functions
    "count", "avg", "min", "max", "sum",
    # Mathematical & Utility Functions
    "abs", "round", "floor", "ceil", "coalesce",
    # String / Date Functions
    "lower", "upper", "to_char", "date_trunc", "extract",
    # PostGIS Spatial Functions
    "st_dwithin", "st_within", "st_intersects", "st_distance",
    "st_makepoint", "st_point", "st_setsrid", "st_astext", "st_asgeojson"
}
```

Any function call not present in `ALLOWED_FUNCTIONS` (e.g., `version()`, `pg_sleep()`, `eval()`, `query_to_xml()`) is rejected with error code `UNSAFE_FUNCTION`.

---

## 8. CTE and Subquery Policy

Common Table Expressions (`WITH ... AS (...)`) and subqueries in `JOIN`, `FROM`, or `WHERE` clauses are fully supported, provided:

1. The outer query and all inner CTE/subquery expressions are `SELECT` statements.
2. All tables referenced within CTEs/subqueries are in `ALLOWED_TABLES`.
3. All columns referenced within CTEs/subqueries exist in `ALLOWED_COLUMNS`.
4. CTE aliases (e.g., `WITH temp_summary AS (...)`) are recognized as valid transient identifiers during traversal so legitimate subquery joins do not trigger table whitelist errors.

---

## 9. Error Categories

The validator returns structured, deterministic error responses using the `ValidationErrorCode` enum:

| Enum Code | Description |
| :--- | :--- |
| `EMPTY_SQL` | Query string is empty, `None`, or whitespace-only. |
| `PARSE_ERROR` | SQL syntax error or failure by `sqlglot` to parse AST. |
| `MULTIPLE_STATEMENTS` | Query contains more than one SQL statement (separated by `;`). |
| `NON_SELECT_STATEMENT` | Statement root is not a `SELECT` (e.g., `INSERT`, `DROP`, `UPDATE`). |
| `UNAUTHORIZED_TABLE` | Query references a table outside `ALLOWED_TABLES` or catalog schemas. |
| `UNAUTHORIZED_COLUMN` | Query explicitly references a column not present in the target allowed table. |
| `UNSAFE_FUNCTION` | Query invokes a function outside `ALLOWED_FUNCTIONS` (e.g., system routines). |
| `UNSAFE_CONSTRUCT` | Query uses forbidden syntax constructs such as `SELECT INTO` or `COPY`. |
| `INVALID_SCHEMA_REFERENCE` | Query references unauthorized schemas (e.g., `pg_catalog`, `information_schema`). |
| `LIMIT_EXCEEDED` | Limit requested exceeds maximum allowed threshold (capped automatically). |

---

## 10. Query Timeout Policy

While `DeterministicSQLValidator` performs static AST analysis without opening database connections or executing queries, it produces a structured `SQLValidationResult` that contains metadata for the downstream execution layer:

```python
@dataclass
class SQLValidationResult:
    valid: bool
    sql: str | None  # Raw input SQL
    normalized_sql: str | None  # Validated, AST-transformed, and LIMIT-injected SQL
    errors: list[str] = field(default_factory=list)
    error_codes: list[ValidationErrorCode] = field(default_factory=list)
    warnings: list[str] = field(default_factory=list)
    statement_timeout_ms: int = 5000  # Enforced 5-second statement timeout for execution
```

The downstream execution layer (Phase 3.3/3.4) **must** issue a `SET LOCAL statement_timeout = 5000;` or pass `statement_timeout_ms` to PostgreSQL for every query execution.

---

## 11. What the Validator Does NOT Guarantee

To ensure accurate security boundaries, the following non-goals are explicitly recognized:

1. **Semantic / Logical Query Correctness**:
   - The validator checks schema validity, structural safety, and resource limits. It does **not** evaluate whether a valid query (e.g. `WHERE latitude = 999`) returns useful oceanographic data.
2. **Infinite Loop Prevention in Complex Recursive CTEs**:
   - While recursive CTEs are constrained by `statement_timeout_ms` (5000ms) and table/column bounds, static analysis does not execute the recursion to count iterations.
3. **Full SQL Injection Elimination at the LLM Level**:
   - If an LLM generates a valid `SELECT` statement with tautological conditions like `WHERE platform_number = '123' OR 1=1`, the validator allows it because it is syntactically safe, read-only, and schema-compliant. Logical SQL injection containment is managed upstream via query understanding and parameterization.

## 12. Examples of Accepted and Rejected SQL

### Accepted Queries

```sql
-- 1. Simple SELECT with WHERE & LIMIT
SELECT platform_number, created_at FROM argo_floats WHERE platform_number = '1900042' LIMIT 10;

-- 2. Hydrographic Observation Query (Auto-injected LIMIT 500)
SELECT profile_id, pressure_dbar, temperature_c, salinity_psu
FROM argo_measurements
WHERE temperature_c > 25.0 AND salinity_psu < 35.0;

-- 3. PostGIS Spatial Bounding Box / Radial Distance Query
SELECT profile_id, platform_number, latitude, longitude
FROM argo_profiles
WHERE ST_DWithin(location, ST_SetSRID(ST_MakePoint(68.5, 12.3), 4326)::geography, 50000);

-- 4. Aggregation with GROUP BY and HAVING
SELECT profile_id, AVG(temperature_c) AS avg_temp, MAX(pressure_dbar) AS max_depth
FROM argo_measurements
GROUP BY profile_id
HAVING AVG(temperature_c) > 20.0;

-- 5. Multi-Table JOIN with CTE
WITH profile_stats AS (
    SELECT profile_id, platform_number, latitude, longitude
    FROM argo_profiles
    WHERE profile_time >= '2024-01-01'
)
SELECT p.platform_number, m.pressure_dbar, m.temperature_c
FROM profile_stats p
JOIN argo_measurements m ON p.profile_id = m.profile_id
WHERE m.temperature_c IS NOT NULL;
```

### Rejected Queries

```sql
-- 1. Multi-Statement Injection Attempt -> REJECTED (MULTIPLE_STATEMENTS)
SELECT * FROM argo_profiles; DROP TABLE argo_profiles;

-- 2. Non-SELECT Data Modification -> REJECTED (NON_SELECT_STATEMENT)
DELETE FROM argo_measurements WHERE pressure_dbar > 1000;

-- 3. Unauthorized Table Access -> REJECTED (UNAUTHORIZED_TABLE)
SELECT password FROM users;

-- 4. Non-Existent Column Reference -> REJECTED (UNAUTHORIZED_COLUMN)
SELECT depth FROM argo_measurements;

-- 5. System Catalog Inspection -> REJECTED (UNAUTHORIZED_TABLE / INVALID_SCHEMA_REFERENCE)
SELECT table_name FROM information_schema.tables;

-- 6. System Function Execution -> REJECTED (UNSAFE_FUNCTION)
SELECT version(), pg_sleep(5);

-- 7. SELECT INTO Construct -> REJECTED (UNSAFE_CONSTRUCT)
SELECT platform_number INTO temp_floats FROM argo_floats;
```

## 13. Test Coverage Summary

The test suite in `tests/test_sql_validator.py` contains **37 unit tests** covering all security requirements and edge cases:

- **Basic Valid Queries** (7 tests): Simple SELECT, WHERE, LIMIT, ORDER BY, Aggregations, GROUP BY/HAVING, JOINs.
- **FloatChat Domain Queries** (7 tests): Profile, measurement, temperature/salinity/pressure filtering, temporal queries, PostGIS spatial queries, measurement aggregations, CTEs/subqueries.
- **Rejections & Edge Cases** (15 tests): Empty/whitespace SQL, syntax errors, multi-statements, INSERT/UPDATE/DELETE/DROP/ALTER/TRUNCATE/CREATE, unauthorized tables (`users`), catalog access (`pg_catalog`, `information_schema`), unauthorized columns (`depth`, `qc_flag`), `SELECT INTO`, unsafe functions (`version()`, `pg_sleep()`).
- **Security Boundaries** (4 tests): Nested unauthorized tables in JOINs, unauthorized tables inside CTEs, subquery table validation, unauthorized schema references (`public.users`).
- **LIMIT Enforcement** (4 tests): Automatic default limit injection (500), capping excessive limit (5000 -> 1000), valid custom limit retention (50), multi-statement check with limit.

**Overall Test Suite Result**: 66 passed tests (37 validator tests + 29 existing database/pipeline tests) with **100% pass rate** in `6.883s`.
